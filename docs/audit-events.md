# Audit events: shared contract

Every Hirewall service records what its agents and humans did as **audit events** in one shared shape. People
Analytics reads them for the Overview page (weekly activity, approvals, Q&A, blocked messages, hours-saved estimate).
Until `backend/core/audit` exposes a reader, the analytics service reads `data/runtime/audit_events.jsonl`
(one JSON object per line). The demo file is generated by `scripts/generate_people_data.py` and every line there
carries `"synthetic": true`.

## Fields

| Field | Type | Required | Notes |
|---|---|---|---|
| `ts` | ISO 8601 datetime with offset | yes | when it happened, e.g. `2026-10-27T09:14:00+01:00` |
| `event` | string | yes | one of the event names below |
| `actor` | `agent` \| `human` | yes | who did it; a human decision is always `human` |
| `reason_code` | string | yes | short machine code, never free text |
| `job_id` | string | no | e.g. `job-be`, same ids as `data/screener_mock/jobs.json` |
| `candidate_ref` | string | no | **pseudonymous** reference (e.g. `C-4821`), never a name or email |
| `outcome` | string | no | result of the action, see the table |
| `topic` | string | no | `kb_question` only: policy topic such as `leave` |
| `synthetic` | boolean | no | `true` for generated demo data; omit or `false` for real events |

Never put names, emails, message text, questions, answers or scores in an audit event.

## Event names

| Event | Emitted by | actor | Typical reason_code | outcome |
|---|---|---|---|---|
| `resume_screened` | screener | agent | `screened` | |
| `candidate_shortlisted` | screener | agent | `score_above_threshold` | |
| `invitation_created` | scheduler (HR clicked Invite) | human | `hr_invited` | |
| `booking_created` | scheduler | agent | `candidate_confirmed` | |
| `booking_cancelled` | scheduler | human | `hr_cancelled` | |
| `reminder_drafted` | scheduler / drafter | agent | `no_reply_48h` | |
| `approval_decided` | approval queue | human | `queue_review` | `approve` \| `edit` \| `reject` |
| `kb_question` | employee_qa | agent | `kb` | `answered` \| `escalated` (plus `topic`) |
| `message_blocked` | any security gate | agent | `injection_suspected`, `rate_limited`, `message_too_long`, `invalid_token`, ... | |

## Screener events in the audit log

These go to the hash-chained log in `core/audit`, shown on the approvals page. They are not part of the analytics feed
above. Each entry holds IDs, flags and counts only, never text or file names.

| Event | When | Fields |
|---|---|---|
| `screener.candidate_ingested` | a resume is accepted | `candidate_id`, `source`, `injection_flag`, `hidden_text_removed`, `extraction_failed` |
| `screener.run_finished` | a scoring run ends | `run_id`, `job_id`, `status`, `scored`, `reason_code` |
| `screener.identity_revealed` | HR reveals an identity | `candidate_id`, `reviewer` |
| `screener.contact_used` | an address is looked up for an approved decision | `candidate_id`, `run_id`, `purpose` |
| `executor.notification` | a candidate was told about a decision | `approval_id`, `action_type`, `candidate_id`, `outcome` |
| `screener.job_extracted` | an offer becomes a draft | `job_id`, `extraction_failed`, `flagged_requirements`, `injection_flag`, `hidden_text_removed` |
| `screener.job_published` | HR publishes an offer | `job_id`, `flagged_requirements` |
| `screener.job_closed` | HR closes an offer | `job_id` |
| `screener.application_received` | an application is linked | `application_id`, `job_id`, `candidate_id`, `source`, `repeat`; for applicants also `reference_id`, `cover_letter`, `cover_letter_failed`, `injection_flag`, `hidden_text_removed` |
| `screener.application_rejected` | a CV fails after the applicant was answered | `reference_id`, `job_id`, `reason_code` |

## Example

```json
{"ts": "2026-10-27T09:14:00+01:00", "event": "approval_decided", "actor": "human", "reason_code": "queue_review", "outcome": "edit"}
{"ts": "2026-10-27T10:02:00+01:00", "event": "kb_question", "actor": "agent", "reason_code": "kb", "outcome": "escalated", "topic": "benefits"}
```

## How analytics uses them

- Weekly counts per event (Monday to Sunday weeks), approvals split by `outcome`, Q&A answered vs escalated,
  blocked messages by `reason_code`.
- Hours-saved estimate: minutes per event (configurable in `backend/services/analytics/config.py`):
  `resume_screened` 6, `booking_created` 4, `kb_question` with outcome `answered` 3, `reminder_drafted` 2,
  `approval_decided` 1.
